## Reconstructed customer/worker journey (verified from legacy code, not production telemetry)

| Journey stage | Legacy observed logic | JODLO implication / approval boundary |
| --- | --- | --- |
| Worker service creation | Android `GuidedAddPostActivity` stages: choose work/category, experience, location, review; `PostCreateCoordinator` validates/handles location, processed images, idempotent `createPost` call. Backend validates category, price, location/contact redaction and image ownership/moderation. | Design a new lightweight worker opt-in (already private `draft`) and eventual listing lifecycle. **M-003** before any location collection and **M-005** before real listings/categories/price rules; **M-004** before UI. No required GPS or image/price fields assumed. |
| Discovery, guest vs signed in | `HomePosts.getNearbyPosts` has a guest *public-feed preview* branch and signed-in *recent trusted location/geohash* branch. It enforces capped searches/pages; guest projection masks location. Localized catalog searches use typed taxonomy and `fwMatcherEngine` separates Hindi/Hinglish generic speech words from actual trade/category intent. | Existing JODLO `/api/v1/catalog/search` has public taxonomy only. Explore text/category and area-first discovery without forced precise GPS. Advanced Hindi intent matching is a **future proposal**, not a copied vocabulary/data set. |
| Visibility & trust | A post can be shown when available, moderation not hidden/removed, owner account active. Owner/admin reactivation runs the same category/location/media validation. Legacy computed trust labels from call activity or profile state. | JODLO worker opt-in is never public or verified automatically. Recheck publication, moderation, worker+owner status and eligibility at interaction time. **Never** automatically import legacy trust labels/ratings. M-005 controls disclosure and trust definitions. |
| Contact request (Nok-Nok) | Signed-in requester sends against receiver's existing available post; server checks both active, not self, **both directions of block**, post owner/status, idempotent pending replay and per-pair cooldown. These mutable facts are re-read inside transaction, then best-effort push occurs after commit. Receiver can accept/decline. | Preserve contact safety, replay protection and transaction-time revalidation as design invariants, but **do not** assume Nok-Nok branding, exact cooldown or final request states. Existing JODLO request contract is pure only. M-005 must define channel/lifecycle. |
| Calls | `requestCall` validates server-resolved caller, receiver+post, both-way block, active call locks, quota and replay; `acceptCall` rechecks mutable state transactionally. Delivery acknowledgment, timeouts, terminal reconciliation and participant-readable projection avoid ghost ringing/stale updates. | Keep idempotency, anti-double-accept, retry, expiry, and terminal cleanup as future RTC test requirements. Don't transplant Agora/FCM/paid-seconds/Razorpay; M-006 provider/payment review later. **No charge for mere ringing**. |
| Data/privilege boundary | `PostDetail` denies unavailable posts to non-owners and derives contact capabilities from relationship. `callPublicProjection` allowlists read fields and uses source ordering/tombstones. | JODLO uses server-owned account/session and narrow public projections; no private Google sub, raw phone/GPS, internal balances, moderation/admin data on discovery endpoints. |

## JODLO implementation bridge — what this milestone actually adds
- New from scratch: `apps/api/src/modules/interactions/contact-safety.ts` is a **pure deny-by-default guard** for future contact decisions. It requires trusted actor/owner IDs, listing ownership, active parties, worker opt-in **and** explicit publication, availability, moderation approval, no bilateral block and approved channel.
- Every flag must be an explicit server-verified boolean; `false`/missing rejects. A stale browse result must never authorize contact. Future D1 adapter must re-read these facts **inside the same transaction** as the request write; this test-only function is not a transactional implementation.
- Tests are synthetic with anonymous opaque IDs; no real users, worker listings, public contact/Nok-Nok API, request lifecycle, location/GPS, FCM, calls, image content or payment.
- Prefer JODLO's already-built shared identifiers, typed pure request-state/CAS decisions and candidate filter rather than duplicating code.

## Explicitly **NOT** decided or migrated
No Firebase/Firestore schema, no legacy auth/OTP, no legacy Razorpay, no automatic call billing/price/reward scheme, no Google Maps/Agora/FCM integrations, no legacy artwork/animations, no old worker trust badges. **M-003** locality/consent/retention and **M-005** pilot matching/publication/calling workflow require the founder's explicit decisions before concrete request/listing storage. **M-004** before Android/web UI, **M-008** real Google OAuth, **M-007** production-only deployment.

**Confidence boundary:** Source inspection demonstrates legacy code paths, not how actual users behaved in production, conversion/reliability metrics or correctness of production configuration. Do not describe it as observed live traffic. Reinspect when legacy source changes; never edit legacy repositories.

## 2026-10-27 — Original JODLO spoken-query prototype (non-migrated)

The legacy matcher treated Hindi voice grammar and Roman Hindi intent words as low-signal while emphasizing the work/category term. JODLO builds **its own** tiny safe phrase analyzer (no copied legacy vocabulary) for public category search in `catalog/search-phrases.ts`, matching all remaining category terms and returning nothing for unspecific or unresolved multi-trade phrases. No actual microphone, speech recognition, offline model, worker discovery or old data migrated. CI verification pending; M-005 founder policy still controls future synonym/category/voice experience.
