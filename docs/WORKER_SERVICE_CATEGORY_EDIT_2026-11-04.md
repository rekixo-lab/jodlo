# JODLO Owner Service Category Edit — 4 November 2026

## Fully connected Category-edit milestone

Starting with the previous native Guided Worker review/publish/owner unpublish (#227), an authenticated JODLO Worker can now **correct the approved Category of an existing service** without deleting it, creating a new listing reference or adding sensitive service fields.

**Customer/Worker journey:** Google Login → opt into Worker draft → list owner services (paged) → select existing service → Edit my service category → search/browse approved active Hindi or English Categories → select different Category → review exact replacement and immediate public change → explicit Save. The server uses an owner-authenticated `PUT /api/v1/me/listings` with canonical JSON `{listingId,expectedCategoryId,nextCategoryId}`; no client account ID, phone, GPS, address, rate, experience, image or verification claim can be sent. User can cancel/back without a write. One existing D1 row changes category; its ID, owner, publication/moderation state and creation time stay the same. Public Category listings and anonymous detail are recomputed against current D1 eligibility, so the old Category no longer returns the changed Listing.

**Atomic eligibility/optimistic conflict:** the D1 UPDATE requires the exact old Category, active worker profile and account, moderation allowed, an active approved destination Category, and no other Listing already using that Category for this worker. A foreign ID, stale previous Category, hidden moderation, inactive new Category or duplicate own service gets the same safe failure (HTTP 409) without disclosing the other owner. The D1 unique constraint remains authoritative for concurrent edits; unexpected DB errors fail closed without reflecting SQL details. This is a Category compare-and-swap, **not** a monotonic revision across an A→B→A cycle; full revision-based editing remains a future schema task.

**Android safety and recovery:** native `HttpURLConnection`-supported PUT (not PATCH); bounded JSON body and strict typed response; permission remains within the existing session coordinator. The write scope marks public/owner reads stale when any mutation is attempted and never repeats an uncertain write. Explicit owner read recheck can observe the current category/visibility but cannot prove a lost edit acknowledgement committed. On a 409, tell worker to refresh their own listing and restart review. Memory-only UI review state verifies current owner row, current approved Category page, same account generation and a second explicit confirmation. Old account rows, page changes, or re-entrant taps cannot send a stale edit.

**Regression evidence to obtain:** exact feature-PR and merged-main Foundation + native Android JDK17/21 green; real D1-backed HTTP test for owned edit → fresh public category listing/detail, one current owner page; strict body parser including duplicate keys, unauthorized actor and forbidden fields; Kotlin headless route/repo/session/write scope and account-switch/uncertain cases; Android build. A configured phone with actual OAuth and human-reviewed active Categories must still exercise this journey before production acceptance.

## Boundaries

No new D1 schema or migration, public Worker identity, free-text profile, experience, rate, media, area, live availability/calling or paid service features. This is one real user journey toward complete Finworkar behavior but **not** the old four-step post. Historical Categories cannot be activated without independent review; last real production D1 inventory check was zero approved active Categories. No Cloudflare production deploy, provider credential change or read-only Finworkar repository writes are part of this source milestone.
