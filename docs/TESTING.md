### Real-runtime HTTP empty-body bug uncovered and fixed (same PR #87)

The new workerd test exposed a concrete production API mismatch: `request.body !== null` rejected a legitimate **zero-byte POST** under workerd because that runtime can surface a closed empty Body Stream rather than `null`. The old check affected worker opt-in, logout/logout-all, and owner listing GET/DELETE no-body routes. The Worker router now reuses one small `hasEmptyBody(request)` helper that reads actual stream bytes: `null` and completely empty streams are permitted, **any byte** and failed stream reads are rejected; it neither buffers the body nor accepts whitespace as "empty". Google token and listing-publication JSON remain governed by their existing stricter bounded parsers. Two in-process regression tests cover empty-stream opt-in/DELETE and logout/logout-all, plus nonempty request denial. The full local workerd authenticated journey must pass on exact PR-head CI and independently on merged-main CI; do not represent the earlier failed run as green.

## 2026-10-29 — Bounded HTTP body stream progress and fail-closed cancellation (PR #88)

The shared JSON reader for Google sign-in (8 KiB) and worker publication (256 B), plus the previously added byte-empty-body reader for worker opt-in/logout/unpublish, accepted unbounded sequences of **zero-length stream chunks** because the byte counter never advanced. In the JSON reader, every empty chunk also entered an unbounded `chunks` array. The JSON overflow branch additionally `await`ed `reader.cancel()`, which can itself remain pending on a malfunctioning or adversarial stream source. An already-locked body could throw outside the parser's guarded section. These conditions could cause a stalled request or unbounded local work rather than an ordinary sanitized rejection.

The two readers now live in the existing shared `apps/api/src/http/body.ts`, with a single internal limit of **eight empty chunks**. A genuinely byte-empty (null or finite stream) request remains accepted by no-body routes. A ninth empty chunk, any byte on a no-body route, a locked/erroring stream, or overly large JSON is rejected without leaking payloads; the JSON overflow path starts cancellation **without waiting on a potentially non-resolving cancel promise**. Existing 8,192/256-byte limits, exact one-member JSON shape and route/status contracts stay unchanged. Added a focused Node regression suite for empty-framing limits, valid single-field JSON, locked/erroring streams and an intentionally non-resolving cancellation. No new route, migration, dependency or provider.

This is a bounded malformed-stream defense, **not** a network timeout/deadline or proof against all slow-client behavior; Cloudflare/network ingress limits remain separately unverified. No visual Android, new active Category, real login provider, personal area/contact, cloud deployment or legacy Finworkar change. Founder M-003/M-004/M-005/M-007/M-008 gates unchanged. Require exact PR head CI and separate squash-merged-main CI before claiming verified.

## 2026-10-29 — Opt-in public listing keyset pages (PR #89)

The first 25 minimal anonymous worker service listings were previously all a customer could retrieve for an approved active Category; the existing `GET /api/v1/listings?categoryId=...` had no continuation. Added an **opt-in**, backwards-compatible `limit=1..25` and optional `after=<already-public-listing-id>` to the **same existing read-only route**, not a new endpoint, user record, or moderation policy. The response for paged clients is `{listings:[{id,categoryId}],nextCursor:<public-listing-id|null>}`. Requests without `limit` retain the original `{listings}` shape and 25 cap, sort order and no-store header unchanged. Reject unknown, duplicate, missing/invalid and cross-shape parameters. `after` is only accepted with `limit`.

The keyset comparison uses the original indexed `(created_at,id)` order but resolves that tuple **inside D1** from the already-public listing ID + exact Category ID. The cursor contains **only the same anonymous listing ID already returned to the customer**, not a timestamp, owner account, Google subject, address, contact or any other private column. The server applies the exact existing allowed/published/active-account/worker/category eligibility to **every** page and reads at most `limit+1` rows. Invalid/deleted cursor anchors produce an empty next page rather than extrapolating a private ordering key; the client can restart from page one. Concurrent adds/removals do not provide snapshot isolation; pagination is a live current-visibility read.

A new deterministic **synthetic-only** Node integration test pages 40 eligible rows across identical timestamps and changing moderation/owner status, verifies no duplicate/skip, rejects forged/cross-category cursors and query shapes, proves the published partial index, and confirms the legacy DTO. The existing real local workerd + D1 HTTP smoke now also validates actual two-page traversal. No actual JODLO pilot Category seed or remotely available worker is created, and no extra public identity, verified badge, GPS or contact exists. Founder M-003/M-004/M-005/M-007/M-008 remain unchanged; backend and local CI work only. Production release **not** approved.

## 2026-10-29 — Fail-closed publicly eligible listing cursors (PR #90)

**Confirmed boundary gap in the newly added PR #89 pagination SQL:** the outer page query applied the authoritative `PUBLIC_LISTING_ELIGIBILITY` predicate, but its `after` anchor subquery checked only the listing ID + Category. Consequently an existing **moderator-hidden, unpublished or disabled-owner** listing could be supplied as an ID to resolve its internal creation timestamp and traverse later eligible listings. The response still contained only eligible public rows, but a nonpublic anchor could act as a private existence/ordering oracle, contradicting the documented "already-public cursor" contract.

The `CONTINUED_PUBLIC_LISTINGS_QUERY` anchor now joins the same existing `accounts`, `worker_profiles` and `categories` relations and applies **exactly the shared `PUBLIC_LISTING_ELIGIBILITY` constant within the same SQL statement** used to fetch the page. Only a *currently* public listing in the same Category can serve as an anchor. A hidden/unpublished/disabled/deleted anchor instead yields `{listings:[],nextCursor:null}`; the caller can restart from page one. This is intentionally a live view, not a snapshot/opaque secret cursor, and the original nonpaged 25-row DTO and indexed order remain untouched. No timestamps, worker accounts or moderation reasons are returned.
