# JODLO — Parent-scoped Search phrase review (2026-10-28)

**State: source reference only. No approved phrase, new search alias, category, service activation or D1 seed.** This is a transparent editorial candidate *work queue*, not the shipped JODLO matcher or a proof of safe meaning.

## Problem

One human phrase can appear in the historical bilingual catalog under multiple different Categories. A global dictionary mapping every such label to one Category would yield false-worker results, the very marketplace failure the founder wants to avoid. Individual legacy Service reviews identify flags but a human needs a **phrase-first view of all possible parents** to resolve collisions safely.

## New source-pinned offline review

Run `npm run reference:phrase-summary` for a compact diagnostic summary and `npm run reference:phrases > phrase-review.json` to produce the full **offline** phrase-group work queue. `npm run reference:check` now asserts both the previous source hash/leaf/category review invariants and the phrase group totals.

Each record has `locale` (`en` or `hi` only), accent-preserving NFKC/lowercased `normalizedPhrase`, all `originalSpellings`, **all historical Group/Family/Category/Service parent references**, list `candidateCategoryIdsForHumanReview`, flags, and mandatory `UNAPPROVED_HUMAN_LANGUAGE_AND_PARENT_SCOPE_REQUIRED` state. The "candidate" IDs mean *possible old parents for an editor to check*, NEVER a guessed search result or permission to publish.

- Multiple Services within a **single** Category are tracked without conflating them with cross-trade collisions.
- A phrase in two or more **different** Categories gets a mandatory `MULTIPLE_DIFFERENT_PARENT_CATEGORIES` flag. It must not auto-select either trade; future reviewed UX needs disambiguation.
- Historical mixed-script Hindi phrases and invalid old leaf-ID shapes remain review flags. Nothing transliterates source text or adds Romanized-Hindi to JODLO.
- The CLI produces no matcher index, SQL, dynamic public route, Cloudflare calls, GPS, worker data or activation status. It does not automatically accept entries without ambiguity.

Every distinct phrase group remains unapproved. Actual unique phrase group count is generated by the source-pinned CLI instead of inventing a count in documentation.

## Proper follow-up

Human reviewers can now take one phrase and inspect all historic category contexts; after a separate founder M-005 policy and native-language review, future service aliases should be explicitly scoped to a single approved Category and protected against cross-parent collisions. Customers will then be able to confirm ambiguous tasks rather than seeing arbitrary results.
